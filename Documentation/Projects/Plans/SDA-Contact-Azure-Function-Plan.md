# SDA Contact Azure Function Plan

Build a small JavaScript Azure Function that accepts the existing SDA contact form and submits one plain-text message to **contact@sda.studio**. Use Azure Functions Flex Consumption with no always-ready instances. Keep the static website and the full C# PublishGraph application separate.

This is a future implementation plan for SDA-CONTACT-PLAN-04. Planning authorizes no implementation, provisioning, DNS changes, outgoing messages, deployment or Git publication. Independent D1–D8 READY binds an exact revision; execution also requires the user's execution request. Document readiness does not establish working software or delivered mail. SP-01/SP-02 and the worker/reviewer cycle govern the later execution and independent R1–R8 result review; the coordinator retains registration and evidence in the [existing Working record](../Working/SDA-Standalone-HTML-Planning-2026-11-16.md#contact-mail-plan-registration).

Existing edits are limited to the contact page, a narrowly scoped exclusion in the preview helper, and the [static README](../../../Static/SDA-Standalone/README.md) plus affected checks. Retain original bytes under SP-01 safeguards. Preserve all other pages, routes, layout, 133 original iframe elements, source captures and historical evidence/manifests. Use app-only authentication with the Function's managed identity, an Exchange Online `Application Mail.Send` role scoped to the selected sender, and a tenant administrator's authorization. Verify the mailbox is in scope and an unrelated mailbox is out of scope. Remove additive unscoped Entra mail permissions; scoped RBAC does not constrain independent broad grants. Do not assume that an address or shared mailbox implies a usable licensed sending setup. [Graph sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0), [Exchange application RBAC](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac).
2. **Transactional alternative:** if the Microsoft 365 prerequisites are absent, select Resend with an owner-approved account, a sending-only API key and a verified owner-controlled sender domain or subdomain. Call `POST https://api.resend.com/emails` with `from`, `to`, `reply_to`, `subject` and `text`. Verify the required DNS records without replacing the existing incoming-mail MX configuration. Domain choice and DNS changes remain explicit prerequisites, not presumed access. Its current free transactional tier is 3,000 messages/month with a 100/day limit; verify account quotas and pricing again at execution. Existing discovered dev/test/prod Frame resources are not authorization to reuse or overwrite them. No production SDA website target is selected yet; website publication remains dependent on that choice.

Use Functions host v4, Node.js **24 GA**, the v4 JavaScript programming model and Linux Flex Consumption, initially 512 MB with always-ready count zero. Resolve the region using `az functionapp list-flexconsumption-locations`; Flex is not available in every region. Do not use legacy Linux Consumption to obtain Node 24. ## HTTP and message contract

Use the Function's direct HTTPS endpoint `POST https://<chosen-function-host>/api/contact`, `authLevel: anonymous`. The public browser holds no Function key or mail credential. Keep the endpoint explicit in contact-page configuration; do not assume Flex supports a particular Static Web Apps linked-backend arrangement.

Accept only `application/json` (optional UTF-8 charset), no compressed request bodies, maximum 16 KiB **actual decoded request bytes**, enforced with a bounded stream read before JSON parsing even if Content-Length is absent or false. Accept a plain object with exactly the fields below; reject extra properties including `to`, `from`, `cc`, `bcc`, headers and attachments. No numeric/string coercion. Trim outer whitespace on names/email/message; count string limits as Unicode code points after trimming, and require nonempty text.

| Existing form control | Public JSON field | Required server rule |
| --- | --- | --- |
| `akID[37][value]` First Name | `firstName` | String, 1–100 characters; reject CR/LF and control characters |
| `akID[38][value]` Last Name | `lastName` | Same rule as first name |
| `akID[39][value]` Email Address | `email` | String, <=254 characters; exactly one conventional ASCII mailbox address, no display name/list, whitespace, CR/LF or control characters; use a maintained email validator with UTF-8 local parts disabled |
| `akID[40][atSelectOptionValue][]` Subject | `subjects` | Array of 1–6 unique strings from the mapping below; reject unknown/duplicate values |
| `akID[41][value]` Message | `message` | String, 1–5,000 characters; preserve line breaks, reject NUL and controls other than tab/CR/LF |
| New Turnstile widget token | `challengeToken` | Nonempty string <=2,048 characters; server verification required |

Translate captured checkbox values to stable public values in the browser: `63` → `membership` (Membership Inquiry), `66` → `artist` (Artist Inquiry), `64` → `commission` (Commission Inquiry), `65` → `sda-frame` (SDA-Frame Inquiry), `89` → `collectors` (Collectors Inquiry), `90` → `other` (Other). The server independently allowlists these values and uses its own labels in a fixed order. All six labels and multiselect behavior remain visible.

Set recipient from a **server constant** `contact@sda.studio`, never request input or a browser setting. Set From only from the verified configured sender; put the validated visitor email in structured Reply-To. Use fixed subject `SDA website contact inquiry`; place first/last name, email, selected labels and message in a labeled plain-text body. Use structured provider JSON, no raw SMTP/header concatenation or HTML interpolation. Never fetch visitor URLs or send to visitor-supplied addresses.

Return JSON with `Content-Type: application/json` and `Cache-Control: no-store`. Application responses use `{ "ok": false, "code": "...", "message": "...", "requestId": "..." }`; validation may add `fields` keyed only by the six public field names, with readable static instructions and no echoed input. Success is HTTP 202 with `{ "ok": true, "status": "accepted", "requestId": "..." }` **only after the provider accepts**. This means accepted for sending, not inbox delivery. Generate the correlation ID on the server; never expose credentials, stack traces, provider response bodies or account identifiers.

| Status | Public code and behavior |
| --- | --- |
| 400 | `invalid_json` or `validation_failed`; show field instructions |
| 403 | `origin_not_allowed` or `challenge_failed`; no provider call |
| 405 | `method_not_allowed`, `Allow: POST, OPTIONS` |
| 413 / 415 | `request_too_large` / `unsupported_media_type` |
| 429 | `daily_limit`; Retry-After seconds until next UTC day |
| 503 | `temporarily_unavailable` for disabled sending, challenge/storage failure or definite provider refusal; no acceptance claim |
| 504 | `send_outcome_unknown` if the provider call times out or disconnects after initiation; explain it may have been accepted |
| 500 | `unexpected_error`; generic text and correlation ID |

Host/platform errors may be non-JSON; the browser must handle these without claiming success. OPTIONS is handled before body/challenge logic: approved origin and POST/content-type preflight only, 204 without mail; otherwise reject. Restrict CORS to exact selected production origins, and only explicit loopback origins in the development environment. Also check Origin on POST against that environment's allowlist; reject absent/null/disallowed values. Do not enable credentials or wildcard CORS. Origin checks constrain browser use; arbitrary clients can forge Origin and must still pass server validation/challenge/cap.

## Abuse limits and privacy

Replace the captured CAPTCHA with Cloudflare Turnstile Managed, action `contact`, configured for the selected website hostname. Keep the public site key in the contact page and secret in server settings. Before any send reservation, POST the token and secret to Siteverify; require `success`, exact expected hostname and action. Reject expired/invalid tokens, and fail closed on errors. Reset the widget after attempts. Tokens expire after five minutes; Cloudflare documents eventual consistency for reuse detection, so do not claim the challenge supplies an atomic duplicate-send guarantee. Do not send a visitor IP to Siteverify or trust forwarded IP headers for this plan. Local testing uses injected verification mocks, never a production bypass setting. [Turnstile server verification](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

Start with a **global maximum 50 provider send attempts per UTC day** across this app, after validation and successful challenge. Use one Azure Table Storage table in the Function's storage account; managed identity gets the needed table data role. Partition key `contact`, row key UTC `YYYY-MM-DD`, properties only count and date. Reserve before calling the provider: conditional insert count=1 if absent; otherwise read, reject count>=50, and update count+1 with the exact ETag (`If-Match`, never wildcard/upsert). On insert conflict/412, reread and retry at most three times; on exhausted contention or uncertain storage outcome, fail closed with 503 and do not send. Never refund a reservation after provider failure, timeout or process crash. A new date gets a new row, with no read-reset race. Test concurrent independent handler instances at the boundary. [Table conditional updates](https://learn.microsoft.com/en-us/rest/api/storageservices/update-entity2).

The table stores daily aggregates only, no name/email/message/token/IP. Retain these small nonpersonal aggregate rows for operational cost comparison; they grow at most one row per active day and need no cleanup service. This cap bounds mail attempts, not incoming HTTP/challenge/compute charges or all bot traffic. Challenge failures consume no send quota. A successful attacker can exhaust daily availability; the initial small contact service accepts that limitation. No per-IP throttle, durable enquiry queue or exactly-once promise is introduced.

Use server settings for `MAIL_ENABLED` (default false), fixed verified `MAIL_FROM`, provider-specific authentication, Turnstile secret/expected hostname, allowed origins and table configuration. The recipient is not configurable. Use managed identity for Azure storage and the Graph branch; a Resend key lives only in Function app settings with restricted operator access, never committed or shipped in static assets. Add Key Vault only if existing organizational secret handling requires it. Local settings are ignored; examples contain names/placeholders only.

Log correlation ID, status/code, duration and coarse dependency outcomes, without bodies, names, email, message, challenge tokens, credentials, raw IPs or provider payloads. Disable body/secret logging and verify dependency telemetry redaction before activation; retain operational logs for 30 days and configure sampling and a small ingestion cap. Mail necessarily persists with the selected provider and recipient; confirm their retention and update the form's short privacy notice accordingly. Disable open/click tracking for this transactional message. No application store of contact content.

## Browser behavior

Give this form a stable contact identifier. Remove its stale action, inline submit blocker and `data-static-submit` hook; make the preview helper skip only that identifier. Load `contact.js` only on this page. Add semantic `required`, `maxlength`, email and subject-group validation, labels and an accessible live status/error region while retaining existing theme classes. Remove obsolete CAPTCHA image/input and its stale requirement; add the real challenge and a short third-party/privacy notice.

Initially keep Submit disabled until the contact handler, endpoint configuration and challenge are ready. Use a `noscript` notice and visible `mailto:contact@sda.studio` fallback. On submit, prevent navigation, validate, disable Submit and mark the form busy, then perform one fetch. Focus the first invalid field/group. Display server text through textContent, never HTML. Restore the button on error; keep visitor input and selected subjects. Reset the challenge for a fresh token before a manual retry.

On HTTP 202 with the expected success shape, show “Your inquiry was accepted for sending. Thank you.” and clear names/email/message/selections plus the challenge. Other responses never clear the form. Use a 30-second browser timeout; server dependency calls use finite timeouts (challenge 5 seconds, storage/retries 5 seconds total, provider 10 seconds). A browser timeout, invalid response or network failure has uncertain outcome: retain input and say “We could not confirm the result. Your inquiry may have been accepted; retrying may send a duplicate.” Do not retry automatically. An in-flight flag prevents duplicate clicks/Enter submission in one page, but refreshes, separate tabs and manual retries can duplicate messages. No claim of exactly-once delivery.

## Cost and rollback

Flex on-demand currently includes 250,000 executions and 100,000 GB-s monthly per eligible pay-as-you-go subscription, shared across its apps. At an illustrative 1,000 submissions/month × 2 seconds × 0.5 GB, contact execution uses about 1,000 GB-s; invalid traffic and cold/dependency time also count. Storage, transactions, logs, networking and the mail provider are additional, and existing apps may consume the grant. This supports a low-cost starting point, not a total-free guarantee. [Functions pricing](https://azure.microsoft.com/en-us/pricing/details/functions/).

At deployment choose a small explicit monthly budget with the owner and alert at 50%, 80% and 100%; add alerts for repeated 5xx/challenge failures and daily-cap exhaustion. Budgets, sampling and ingestion limits are not a hard Azure spend stop. Use the 50/day application cap below Resend's current free daily quota, account for other account traffic, and leave provider paid overages disabled where available. Recheck regional prices and account entitlements before enabling.

Rollback order: disable contact submission and show the email fallback; set `MAIL_ENABLED=false`; if necessary stop only the new Function. Revert owned contact/helper bytes from retained preimages or redeploy the prior reviewed package/config, preserving counters and evidence. Revoke/rotate a compromised provider secret separately. Do not delete shared resources or modify Frame services. A rollback cannot recall accepted mail; any unknown-outcome request remains unknown. Operator handoff includes selected resources/provider/sender/origins, secret rotation method, budget alerts, diagnostic query using requestId and these disable/recovery steps.
